## 2.1 数据模型的基本概念

**数据模型**（data model）：对**数据特征**的抽象，为数据库系统的信息表示和操作提供抽象框架，是数据库系统的核心与基础。【db02 P4】

【定义】描述**数据的结构**，定义在该结构上可执行的**操作**，以及数据之间必须满足的**约束条件**。【db02 P5】

**数据模型三要素**：
- **数据结构**：描述数据的类型、内容、性质及数据间的联系——是数据模型的基础，也是不同类型数据模型的划分依据【db02 P6】
- **数据操作**：在相应数据结构上可以执行的操作类型与操作方式【db02 P7】
- **数据约束**：确保数据的正确、有效与相容【db02 P7】

**对应关系与理解要点**（课堂补充）：
- **概念模型**：现实世界 → 概念世界的抽象，与具体 DBMS 无关，面向用户
- **逻辑模型**：对应三级模式中的**模式**（数据库全局逻辑结构，用 DDL 定义）
- **物理模型**：对应**内模式**（存储结构与存取方法）
- **外模式**：从模式按用户需求导出的子集，每个用户（组）一个

## 2.2 数据模型的四个世界

> 现实 → 概念 → 信息 → 计算机，是一个**逐步转化**的过程。

| 世界 | 内容 | 关键特征 |
| ---- | ---- | ---- |
| **现实世界** | 用户需求：数据需求、处理要求 | — |
| **概念世界** | 对需求分析提纯后，用所选概念数据模型的术语统一表示基本概念与关系 | 与具体 DBMS 和计算机**无关** |
| **信息世界** | 概念模型的细化 + 数据库系统一级实现（定义逻辑数据模型） | 与具体 DBMS **有关** |
| **计算机世界** | 物理存储结构描述：文件结构（堆/直接/索引）、索引/集簇设计 | DB 的最终实现结构 |

> "集簇"指数据库中的聚簇/cluster 存储方式，属于计算机世界里的物理存储设计。

## 2.3 概念世界与概念模型（E-R）

概念世界给出数据的概念化结构，一般用**概念模型**表示。这里只讲**实体-联系（E-R）模型** & 扩充的实体-联系（EE-R）模型。

### E-R 模型中的基本概念

**实体**：现实世界中可区别于其他对象的"事物"。
**实体集**：由**具有共性的实体**构成的集合——共性指实体含**相同的属性组成**，但各实体在属性上的取值存在区别。

**属性**：属性可以有值；一个属性可取值的集合称为该属性的**值域/属性域**（value domain）。

**联系**：按涉及实体集的个数分为
- 两个实体集间的联系（**二元联系**）
- 多个实体集间的联系（**多元联系**）
- 单个实体集内部的联系
> 多元联系可拆成多个二元联系，但表达意味上有细微差异。
> 同一实体集之间可有多种联系：e.g. 职工之间既是同事又是上下级。

<mark>**联系的函数对应关系**</mark>（记例子就好理解）：
| 类型 | 含义 | 例子 |
| ---- | ---- | ---- |
| 1:1 | 一一对应 | 居民 ↔ 身份证 |
| 1:m | 一多对应 | 宿舍 : 学生 |
| m:n | 多多对应 | 学生 : 课程 |

**联系所具有的特性**：联系发生时需记录的信息成为**联系的属性**（<font color="red">红色</font>为联系属性）：
- 学习关系（学生，课程，<font color="red">成绩</font>）
- 借阅关系（学生，图书，<font color="red">借阅日期</font>，<font color="red">归还日期</font>）
- 比赛（甲方，乙方，<font color="red">比赛结果</font>）

**实体（集）与属性的描述**：
- 属性描述：**属性名、属性域**
- 实体描述：**实体名**；**实体型** = 实体名 + 一组属性名（描述实体的组成结构信息）；**实体值** = 一个实体全部属性取值构成的集合（在关系模型中称为**元组** tuple）

**联系及连接关系的描述**：**联系名** + 相关**实体集名称** + **联系上的属性** + **函数对应关系**。例：选课联系（学生，课程，成绩）

### E-R 图

**基本图形符号**：实体集=**矩形**，属性=**椭圆**，联系=**菱形**，用线段连接；为刻划函数对应关系，线段边上注明 1:1 / 1:n / n:m。

**属性归属规则**：每个实体集（联系）可以有多个属性，**但每个属性只能隶属于一个实体集（联系）**：

**实际绘制中的设计选择**：
| 纠结 | 判断标准 |
| ---- | ---- |
| 实体 or 属性？ | 实体：需要进一步多方面描述的信息；属性：单一的描述值（非结构化的单值信息） |
| 实体 or 联系？ | 实体：可独立存在的持久对象；联系：因某种需要/事件发生而产生，常与多个对象有关 |
| 二元 or 多元联系？ | 视联系语义与涉及实体个数；只需两两联系且不出现二义性（歧义性）时可用多个二元联系实现 |
| 函数对应关系？ | 基于系统的语义约束来定义 |
| 属性挂实体 or 联系？ | 实体属性：实体内在特征，不因联系出现而改变/消亡；联系属性：描述因联系发生而需要记录的信息，随联系产生而出现、随联系消亡而消亡 |

> 课堂提示：① 先画框架再画属性比较方便；② 系统是动态的，函数关系不能只凭某一时间点的 1:1 / 1:n 断定，实际运行起来也可能是 m:n。

### 课堂练习：体育馆管理系统 E-R 设计

> 按"找关键词 → 概念判断 → 确定联系 → 配属性"四步走

**第 1 步 · 找关键词**：球员、俱乐部、体育馆、比赛、签约

**第 2 步 · 概念判断（难点）**：
- **比赛容易被看成联系，但它是实体**——否则球员与比赛之间的"参加"关系无法表达
- 判定为实体：体育馆、俱乐部、比赛、运动员（球员）

**第 3 步 · 确定联系**（函数对应关系按系统语义）：
| 联系 | 涉及的实体 | 备注 |
| ---- | ---- | ---- |
| 使用 | 体育馆 - 俱乐部 | — |
| 主队 / 客队 | 俱乐部 - 比赛 | 同一实体集（俱乐部）对比赛的两类联系 |
| 签约 | 俱乐部 - 运动员 | — |
| 参加 | 运动员 - 比赛 | — |

**第 4 步 · 配属性**：
- 实体属性：体育馆-地址；俱乐部-地址；比赛-日期；运动员-运动员身体数据
- 联系属性：参加-比赛中球员各项数据；签约-签约日期；使用-使用日期
